> 先建**基线**，再定阈值。禁止在未测之前写死帧率目标。
> 每档重复 3 次，取中位数；每次跑 60 秒后再记第 2 分钟的数据（看是否劣化）。

## 2. 分级负载

用 `tools/gen_ui.py --windows N` 重新生成 UI，再在游戏里创建对应数量窗口（示例脚本见 §4）。

| 级别 | 窗口数 | 控件数 | 设备 | 平均 FPS | 1% Low | `Update` avg (ms) | `Update` P95 (ms) | 内存 60min | 结论 |
|---|---|---|---|---|---|---|---|---|---|
| L1 基础 | 3 | 18 | A | | | | | | |
| L1 | 3 | 18 | B | | | | | | |
| L2 中等 | 10 | 60 | A | | | | | | |
| L2 | 10 | 60 | B | | | | | | |
| L3 目标 | 20 | 120 | A | | | | | | |
| L3 | 20 | 120 | B | | | | | | |
| L4 压力 | 30 | 180 | A | | | | | | |
| L4 | 30 | 180 | B | | | | | | |

判定口径（相对基线）：

- L3 通过：FPS ≥ 基线 −20%，`Update` P95 ≤ 8ms（A）/ 12ms（B），无内存持续增长；
- L4 只用于找拐点，不设通过线；
- 若 L3 不通过，记录拐点（从第几个窗口开始掉），并把 `DEGRADE_WINDOW_COUNT` 调到拐点 −2。

## 3. 降级与恢复

| 步骤 | 期望 | 实测 |
|---|---|---|
| 30 窗口 → 删除到 10 窗口 | 帧率回到 L2 水平（±10%），`Update` 回落 | |
| 关闭阴影/序列帧（低配模式） | 帧率提升，视觉可接受 | |
| 切出/切回游戏 | UI 不丢、窗口位置不漂 | |
| 断线重连 | 窗口表按 `rev` 完整重建 | |

## 4. 负载脚本（开发期，逐条输入）

```
/wxcreate w1 200 120 p20 p20
/wxcreate w2 200 120 p30 p30
...                       # 按目标数量重复，注意玩家配额 8 -> 测 L2 以上需先调高：
/wxaquota <你的名字> 40   # 管理员指令
/wxshake w1 12 5          # 反复触发，观察持续动画时的 Update 耗时
```

> 也可以临时把 `modConfig.MAX_WINDOWS_PER_PLAYER` 调到 40，测完改回。
> 场景窗口（`wxscreate`）配额 24，适合测 L3/L4 而不占玩家配额。

## 5. 采集方式

- `modClient/debugSuite.py` 每 150 帧往日志打一行：`[WX-PERF] frames=... peak_windows=... avg=...ms p95=...ms`；
- 同时用外部工具（MSI Afterburner / 安卓开发者 GPU 渲染条）记录帧率与 1% Low；
- 每档结束把日志段落复制到本表。

## 6. 结论

- [ ] L3 达标 → UI 后端成立，进入 P1
- [ ] L3 不达标 → 记录拐点与降级线，重定目标为"14 窗口 + 低配模式"
- [ ] L2 都不达标 → UI 后端否决，Core 改为"世界内屏幕 + 少量 HUD"
