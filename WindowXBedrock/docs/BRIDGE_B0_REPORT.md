# B0：Bridge（游戏 ↔ 本机 Windows 程序）允许性核查报告

> 结论：**B0 = 有条件不通过（本机直连路径全部无官方 API）**
> 2026-10-26 ｜ 依据：网易开发者官网 ModAPI 索引表（ModAPI 3.9/3.10）+ Apollo SDK 文档 + 本机模板

---

## 1. 核查目标

判断"游戏内指令驱动本机 Windows Companion"是否有**合法且可用**的通道，从而决定项目形态：
D0（仅 Core）/ D1（Core + Companion 各自独立）/ D2（真正联动 = 才可称"移植"）。

## 2. 官方 API 能力证据

| 候选通道 | 官方是否存在 | 证据 | 可用性判断 |
|---|---|---|---|
| HTTP / WebSocket / Socket 客户端请求 | **否** | ModAPI 接口索引（通用分类）无任何网络请求函数 | ❌ 本机直连不可行 |
| 通用本地文件读写 | **否**（只有配置级） | 仅有 `GetConfigData` / `SetConfigData` / `GetModConfigJson`（且限 mod 目录） | ❌ 无法用文件做信箱 |
| 启动外部进程 / 打开网址 | **否** | 索引中无 ShellExecute/URL 类接口；`ImportModule` 只能导入 mod 内模块 | ❌ |
| 剪贴板读写 | **是**（客户端） | `GetClipboardContent` / `SetClipboardContent` | ⚠️ 理论可做极低频通道，但会覆盖玩家剪贴板、隐私差、审核风险高 → **不建议** |
| 游戏内双端事件 | **是** | `NotifyToServer` / `NotifyToClient` / `BroadcastToAllClient` / `BroadcastEvent` | ✅ 仅限游戏进程内，不能出沙箱 |
| Apollo 网络服服务器通信 | **是** | Apollo SDK《服务器通信》：master/service 互发事件；另有外部 HTTP 回调章节 | ⚠️ 只解决"服务器↔外部服务"，且需**网络服**形态 |
| 运行环境探测 | **是** | `GetIP` / `GetPlatform` / `IsInServer` / `IsInApollo` / `GetHostPlayerId` | ℹ️ 只用于判定，不构成通道 |

## 3. 三条可选路径评估

### 路径 A：本机直连（127.0.0.1 / 命名管道）
- 结论：**当前 SDK 无 socket / 文件 / 进程 API → 不可实现**。
- 若未来版本新增，可作为 B1 再验，但**不要用注入/改包/逆向私协议替代**。

### 路径 B：剪贴板信箱 —— **已否决，不采用**
```
游戏客户端 SetClipboardContent("WX|req|...") → Companion 轮询剪贴板 → 执行
```
- 技术上可行（`Get/SetClipboardContent` 存在），但性质是**绕过平台未授权的本机通信**：
  覆盖玩家剪贴板、可被任意软件读取、无法做发送者认证、行为对玩家不可见。
- **结论：否决。** 不实现、不预留开关、不在发布包内保留任何代码。
- P0.5 起 `modConfig.ALLOW_CLIENT_WRITES` 与一切"本机信箱"思路仅作为**反例记录**，不构成开发路径。

### 路径 C：云中继（网络服 HTTP 回调 / 自建中继）
```
客户端指令 → 服务端(网络服) → 中继服务(HTTPS) → Companion 长轮询 → 执行 → 回执
```
- 优点：不触碰本机沙箱，纯"服务器↔外部服务"的常规集成；延迟 200ms–1s，对"窗口震动/移动"够用。
- 前提：**必须是 Apollo 网络服形态**（联机大厅地图通常没有对外 HTTP 能力，待确认）；需要自建中继、会话码鉴权、防重放。
- 风险：玩家需要注册/绑定码；中继成本；审核需说明"外部程序"（仍属未知项）。
- 结论：**若要做 D2，这是首选路径**，但必须平台书面确认 + 自建中继。

## 4. 门禁判定

| 项 | 结果 |
|---|---|
| B0-a 本机直连有无官方 API | **无**（已确证） |
| B0-b 网络服 HTTP 出站 | **有**（Apollo SDK 层），但需确认"组件作品能否使用"与"联机大厅是否支持" |
| B0-c 平台是否允许"作品 + 外部程序" | **未知，必须问询** |
| **综合** | **有条件不通过**：D2 暂不可立项；项目默认按 **D0/D1** 推进 |

**立项规则**：B0 未变成"允许且可复现"之前，不把 Bridge 写进任何对外材料；Companion 与 Core 完全解耦、各自独立可交付。

## 5. 下一步（等待平台答复期间可做的事）

1. Core：继续 P0/P1（UI 后端 + 摄像机 + 指令），不依赖 Bridge。
2. Companion：做 S2（手选窗口 → 移动/震动 → 恢复），独立可用。
3. 若拿到书面许可：优先做**路径 C** 的 30 分钟最小闭环（游戏按钮 → 中继 → Companion 震动一次 → 回执）。
4. **B0 冻结**：在平台给出书面答复前，不实现任何 Bridge 代码（含剪贴板、文件信箱、注入、改包、逆向私协议）。

> P0.5 结论：B0 维持**冻结**。理由：本机直连无官方 API；剪贴板路径属未授权绕过，已否决；
> 云中继依赖网络服与平台许可，均未确认。任何"先做出来再说"的做法都不进入仓库。

> **主题**：关于基岩版组件与"本机桌面辅助程序"联动的合规性咨询
>
> 您好，我们计划开发一个**基岩版玩法组件**（联机大厅地图 + 行为包/资源包），其中包含一个**可选的 Windows 桌面辅助程序**（独立安装，不注入游戏、不修改客户端文件、不读取游戏内存）。想确认以下三点是否允许：
>
> 1. 组件内是否有官方支持的方式与本机进程通信（HTTP/WebSocket/命名管道/文件）？若无，是否允许通过**自建云端中继**（游戏服务器 → HTTPS → 用户本机程序轮询）实现？
> 2. 该外部程序仅执行用户**手动选中**的窗口的移动/缩放等操作，不做屏幕采集、不读取游戏数据，是否需要在作品页额外声明或提交材料？
> 3. 若第 1 点不允许，组件是否可以仅在作品描述中提供"可选桌面增强（站外下载）"的说明链接？（或完全不提，仅保留组件内功能）
>
> 另外，我们计划参考开源项目 WindowX（作者 XuTrain）的行为与参数**独立重写**，不复制其代码与美术资源；其 JAR 内声明 MIT、Modrinth 页面为 Apache-2.0，如需在作品中标注来源，请告知推荐写法。
